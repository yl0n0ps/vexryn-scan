# Vexryn — every forge, every CI, every agent: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (founder's choice: inline, no subagents; final review = `/code-review high` in session). Steps use checkbox (`- [ ]`) syntax.

**Goal:** One line in any CI posts (and keeps up to date) the Vexryn review on the pull/merge request — GitHub, GitLab, Forgejo/Gitea (Codeberg), Bitbucket Cloud, Azure DevOps — and can optionally block the merge. Other CIs get machine-readable output (`--json`) and an exit code (`--strict`). Any MCP agent keeps using `vexryn mcp` (already agent-agnostic), now documented per agent.

**Architecture:** A new `vexryn ci` command: detect the CI from its env → find the PR's base with `git merge-base <target tip> HEAD` → run the existing review → print it → post/update ONE sticky comment through a small per-forge adapter (global `fetch`, no new dependency). GitHub, Forgejo and Gitea share one adapter (same comment API). The GitHub Action switches to `vexryn ci`, which replaces `scripts/pr-review.sh` + `scripts/pr-comment.sh`.

**Tech Stack:** TypeScript/Node ≥18 (global `fetch`), `node:http` mock servers in tests, `node:assert`.

## Global Constraints

- Nothing is sent anywhere but the one comment, to the forge the CI runs for, with the token the user gave. Never print a token; errors show the HTTP status only.
- A `next` page URL is followed only on the API's own origin (a token never leaves for another host). Comment ids used in URLs must be all digits.
- Non-blocking by default: a CI config problem or a refused post → a clear message, exit 0. Only `--strict` turns open ⚠️ findings into exit 1.
- A PR can't approve itself: `--strict` counts ⚠️ findings not accepted by the BASE side's `.vexryn.json` (existing rule); the "`.vexryn.json` accepts N more" notice is shown but doesn't block.
- No new dependency. MCP stays read-only (its schema must not contain wire/trim/wrap/deep/write/ci/post).

## Review Focus

1. `pull_request_target` or a checkout that doesn't contain the PR head → skip with a message, never an empty "no change" review (Task 3 test).
2. A shallow clone where the base commit is missing → a message naming the exact fix per CI, exit 0 (Task 3 test).
3. Someone else's comment starting with the marker → Vexryn's update is refused → it posts its own new comment, never goes silent (Task 2 test).
4. A malicious `next` URL on another host / a non-numeric id in a listing → not followed / ignored (Task 2 test).
5. Bitbucket renders no HTML → the hidden marker must not show as text there (markdown-only marker for Bitbucket; Task 2 test).
